# FurryManager — архитектура

Локальный менеджер референсов и арт-библиотек: продвинутые теги, семантический поиск (CLIP), браузерное расширение для скачивания в один клик, экономное хранение.

**Стек:** Tauri 2 (Rust + веб-фронт) + Python-сайдкар для ML и скачивания. SQLite — единственная БД.

---

```
│                     │   расширения (localhost)│ │

└─────────────────────────────────┼───────────────┘
                        stdin/stdout (JSON-RPC)
                     ┌────────────▼─────────────┐
                     │ Python Sidecar           │
                     │ · CLIP/SigLIP (ONNX)     │
                     │ · WD14-теггер (автотеги) │
                     │ · gallery-dl (скачивание)│

                     └──────────────────────────┘
      ┌──────────────────┐

      └──────────────────┘
```

**Разделение ответственности:**
- **Rust Core** — всё быстрое и надёжное: БД, файлы, миниатюры, API. Работает без сайдкара (деградация: нет ML-поиска и качалки, всё остальное живо).
- **Python Sidecar** — всё «умное»: модели и парсинг сайтов. Один долгоживущий процесс, общение через JSON-RPC по stdin/stdout. Упаковывается PyInstaller'ом, Tauri поставляет как sidecar-бинарник.
- **Frontend** — тонкий, вся логика в Rust.

## 2. Хранение файлов (content-addressed storage)

Оригиналы никогда не изменяются и не переименовываются пользователем — файл лежит по своему хешу:

```
library/
  store/
    ab/abf3c2…d9.png        ← имя = SHA-256, шардинг по 2 символам
  thumbs/
    ab/abf3c2…d9.avif       ← превью 400px, AVIF q60 (~15–40 КБ)
  models/                   ← ONNX-модели (качаются при первом запуске)
  library.db                ← SQLite
```

Принципы:
- **Дедупликация бесплатно:** одинаковый файл = одинаковый хеш = хранится один раз, сколько бы раз его ни импортировали.
- **Папки/альбомы виртуальные** — только записи в БД. Один арт может быть в 10 коллекциях без копий.
- **Два режима импорта:** *перенос* в store (по умолчанию) или *in-place* (файл остаётся на месте, в БД хранится путь + хеш; для тех, кто не хочет отдавать файлы приложению).
- **Превью-кэш** пересоздаваем, можно чистить целиком.
- Оригиналы **не пережимаются**. Опционально (явный опт-ин): lossless PNG→WebP при импорте (−30–50 %).

## 3. Схема БД (SQLite)

```sql
-- Файл как физический объект
CREATE TABLE files (
  id INTEGER PRIMARY KEY,
  sha256 TEXT UNIQUE NOT NULL,
  phash BLOB,                  -- perceptual hash (near-dupes)
  ext TEXT, size INTEGER,
  width INTEGER, height INTEGER,
  kind TEXT,                   -- image | animation | video
  storage TEXT,                -- 'store' | 'inplace'
  path TEXT,                   -- только для inplace
  created_at INTEGER, imported_at INTEGER
);

-- Метаданные источника (один файл может прийти из разных мест)
CREATE TABLE sources (
  id INTEGER PRIMARY KEY,
  file_id INTEGER REFERENCES files(id),
  url TEXT, site TEXT,         -- furaffinity | e621 | twitter | …
  artist TEXT, title TEXT, description TEXT,
  posted_at INTEGER, fetched_at INTEGER
);

-- Теги с пространствами имён (как у Hydrus/e621)
CREATE TABLE tags (
  id INTEGER PRIMARY KEY,
  namespace TEXT NOT NULL DEFAULT '',  -- species | artist | palette | meta | ''
  name TEXT NOT NULL,
  UNIQUE(namespace, name)
);
CREATE TABLE file_tags (
  file_id INTEGER REFERENCES files(id),
  tag_id INTEGER REFERENCES tags(id),
  origin TEXT,                 -- manual | wd14 | source-site
  confidence REAL,             -- для автотегов
  PRIMARY KEY (file_id, tag_id)
);

-- Иерархия и синонимы тегов ("folf" → implies "fox","wolf"; "лис"="fox")
CREATE TABLE tag_relations (
  parent_id INTEGER, child_id INTEGER,
  kind TEXT                    -- implies | alias
);

-- Виртуальные коллекции
CREATE TABLE collections (id INTEGER PRIMARY KEY, name TEXT, parent_id INTEGER);
CREATE TABLE collection_files (collection_id INTEGER, file_id INTEGER, position INTEGER);

-- Векторы CLIP (sqlite-vec)
CREATE VIRTUAL TABLE clip_vectors USING vec0(
  file_id INTEGER PRIMARY KEY,
  embedding float[512]         -- 512 для ViT-B-32; 768 для SigLIP-base
);

-- Полнотекстовый поиск по тегам/описаниям (FTS5)
CREATE VIRTUAL TABLE fts USING fts5(file_id, artist, title, tags_flat, description);

-- Очередь фоновых задач
CREATE TABLE jobs (
  id INTEGER PRIMARY KEY,
  kind TEXT,                   -- embed | autotag | phash | download | thumb
  payload TEXT, status TEXT,   -- pending | running | done | error
  attempts INTEGER DEFAULT 0, created_at INTEGER
);
```

Ключевые решения: `namespace` в тегах даёт «расу/автора/палитру» как первоклассные фильтры; `origin`+`confidence` позволяют скрывать/чистить неудачные автотеги, не трогая ручные; `tag_relations` решает гибридность (тег `species:folf` автоматически находится по запросам `fox` и `wolf`).

## 4. ML-пайплайн (индексация)

Всё — фоновые задачи из таблицы `jobs`; UI никогда не ждёт модель.

**При импорте файла:**
1. SHA-256 → дедуп-проверка (Rust, мгновенно)
2. Превью 400px AVIF (Rust, `image` crate)
3. `phash` — perceptual hash для near-dupes (сайдкар, мс)
4. `embed` — CLIP-эмбеддинг → `clip_vectors` (сайдкар)
5. `autotag` — WD14-теггер → теги с confidence ≥ 0.35 (сайдкар)

**Модели (ONNX, CPU, качаются при первом запуске):**

| Модель | Задача | Размер | Скорость CPU |
|---|---|---|---|
| SigLIP-base / OpenCLIP ViT-B-32 | эмбеддинги для текстового поиска | ~350 МБ | ~10–20 имг/с |
| WD14 (SmilingWolf v3, swinv2) | автотеги danbooru/e621-стиля | ~450 МБ | ~5–10 имг/с |

Для 100k картинок первичная индексация — несколько часов фоном; это нормально, показываем прогресс. Батчинг по 16–32 картинки. GPU (DirectML/CUDA) — опциональное ускорение, не требование.

**Видео:** эмбеддинг и теги по 3–5 кадрам (начало/середина/конец), превью — кадр с 10 %.

## 5. Поиск

Один поисковый бар, три механизма под капотом:

- **Тег-синтаксис:** `species:fox artist:kenket -meta:sketch` → SQL по `file_tags` (+ разворот `implies`/`alias`).
- **Семантический:** свободный текст «рыжий лис в куртке» → CLIP-текст-энкодер → top-K косинусный поиск в `clip_vectors`. Запрос переводится на английский (CLIP обучен на английском) — маленький словарь + опционально локальный переводчик.
- **Гибрид:** теги как жёсткий фильтр, семантика как ранжирование остатка.
- **«Найти похожие»** от любой картинки — два направления:
  - *Локально:* phash (дубликаты/ресейвы, работает уже в MVP) + CLIP-вектор (похожие по стилю/содержанию, с v0.2).
  - *В интернете:* обратный поиск через **Fluffle.xyz API** (фурри-специфичный: FA, e621, Weasyl, Twitter, Itaku), фолбэк — e621 iqdb и SauceNAO. Заодно решает задачу «найти источник и автора».

## 6. Браузерное расширение

Manifest V3 (Chrome/Firefox). Кнопка на странице арта / контекстное меню «Save to FurryManager».

**Транспорт — локальный HTTP, а не native messaging:** Rust core слушает `127.0.0.1:<порт>` с токеном (токен генерируется приложением, вставляется в настройки расширения один раз). Это проще native messaging (не нужны манифесты хоста на каждый браузер) и работает во всех браузерах одинаково.

**Поток:**
1. Расширение шлёт `POST /ingest {url, page_title, cookies?}`
2. Rust создаёт job `download`, мгновенно отвечает — бейдж «✓ в очереди»
3. Сайдкар качает через **gallery-dl** (готовые экстракторы: FurAffinity, e621, Weasyl, Itaku, Twitter/X, Bluesky, Telegram-каналы и ~300 сайтов) вместе с метаданными: автор, теги сайта, описание, дата
4. Файл уходит в обычный пайплайн импорта; теги сайта пишутся с `origin='source-site'`

Для сайтов за логином gallery-dl умеет брать куки из браузера (`--cookies-from-browser`) — решает FA/e621 с возрастными фильтрами.

## 7. Экономия места — сводка

| Механизм | Экономия | Когда |
|---|---|---|
| Дедуп по SHA-256 | точные копии → 0 байт | всегда, автоматически |
| Near-dupe отчёт (phash) | у коллекционеров часто 10–20 % | инструмент «Дубликаты», решает пользователь |
| Превью AVIF вместо PNG-кэша | кэш в ~10 раз меньше | всегда |
| Lossless PNG→WebP | −30–50 % на PNG | опт-ин при импорте |
| Lossy-архивация «холодных» файлов | до −80 % | опт-ин, явно помеченные коллекции |

Философия: по умолчанию не трогаем ни байта оригиналов; всё агрессивное — только явным действием пользователя.

## 8. Роадмап

**MVP (v0.1):** импорт папки → CAS + дедуп → превью-галерея → просмотрщик с проигрыванием видео/GIF → ручные теги с неймспейсами → тег-поиск → «похожие» локально (phash) и в интернете (Fluffle) → онбординг-тур → два режима UI (базовый/продвинутый). Без ML-моделей и расширения. Фронтенд v0.1 — vanilla JS без сборщика: для разработки не нужен Node.js, только Rust.

**UX-принципы (для всех версий):** приложение должно быть понятно человеку, который не знает слов «неймспейс» и «хеш». Базовый режим — галерея, поиск, простые теги, большие кнопки; продвинутый — синтаксис запросов, неймспейсы, batch-операции, настройки хранения. Онбординг при первом запуске: выбор папки библиотеки → короткий тур из 3 шагов → выбор режима. Подсказки в пустых состояниях, человеческие тексты ошибок.

**v0.2 — ML:** сайдкар, CLIP-поиск текстом, WD14-автотеги, «похожие по стилю», очередь jobs с прогрессом.

**v0.3 — качалка:** расширение + gallery-dl, метаданные источников, куки из браузера.

**v0.4 — полировка:** near-dupe инструмент, tag implies/aliases, in-place импорт, watcher папок, lossless-конвертация.

## 9. Риски

- **Scope creep** — главный. Порядок роадмапа жёсткий: галерея с тегами полезна без ML, ML без галереи — нет.
- **CLIP и фурри-арт:** базовый CLIP обучен на фото, на стилизованном арте качество среднее. WD14 обучен на danbooru — с артом сильно лучше. Если текстовый поиск разочарует, план Б: поиск по комбинации автотегов (WD14) вместо чистых эмбеддингов, либо файнтюненный на e621 CLIP (существуют открытые чекпойнты).
- **PyInstaller-сайдкар:** ~150–300 МБ. Приемлемо; альтернатива — качать Python-окружение при первом запуске.
- **Антиботы (Cloudflare на FA):** gallery-dl с куками браузера обычно проходит; фолбэк — расширение шлёт уже загруженные страницей байты картинки.
- **sqlite-vec на 500k+ векторов:** brute-force скан ~сотни мс — терпимо; если нет, мигрируем на HNSW (usearch), интерфейс не меняется.
